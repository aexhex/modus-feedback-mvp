# Техническая концепция

## Компоненты

```
Браузер (SPA, ES-модули)  ──HTTP/JSON──▶  Node.js сервер (node:http)
                                           ├─ routes.js     REST API, конверт { ok, data, error }
                                           ├─ access.js     политика доступа (RBAC + владение)
                                           ├─ routing.js    маршрутизация обращений
                                           ├─ tickets-*.js  жизненный цикл, SLA, комментарии
                                           ├─ analytics.js  показатели, повторяющиеся темы
                                           ├─ escalation.js фоновая эскалация просрочек (раз в минуту)
                                           ├─ export.js     экспорт реестра в CSV
                                           ├─ settings.js   настраиваемые сроки SLA
                                           ├─ collab.js     наблюдатели, приглашения, задача Битрикс24
                                           ├─ home.js       данные главной страницы по ролям
                                           ├─ reports.js    отчёты о внедрении, рейтинг авторов
                                           ├─ surveys.js    опросы сотрудников
                                           ├─ client-feedback.js  публичная форма для клиентов, NPS
                                           ├─ votes.js, digest.js голосование за идеи, сводка недели
                                           ├─ user-import.js, demo-reset.js  импорт из CSV, сброс демо-данных
                                           ├─ templates.js, audit.js  шаблоны ответов, журнал действий
                                           ├─ notifications.js  уведомления + журнал отправки в Битрикс24 (outbox)
                                           ├─ integrations/  Битрикс24 и 1С УТ ──▶ REST вебхук / OData 1С (или демо-портал)
                                           └─ db.js ──▶ SQLite (node:sqlite) + data/uploads/
```

## Выбор технологий

| Решение | Почему |
|---|---|
| Node.js 24+, без внешних зависимостей | Запуск одной командой без `npm install`; нет цепочки поставок для проверки; встроенные `node:sqlite` и `node:test` |
| SQLite | Реляционная модель, транзакции, ноль администрирования для MVP. Схема переносится на PostgreSQL без изменений логики |
| Vanilla JS + ES-модули | Нет шага сборки; интерфейс простой. При росте — React/Vue |
| Хэш-роутинг SPA | Работает на любом статическом хостинге / за любым прокси |
| Графики на чистом SVG | Без библиотек; одна ось на график, подсказки, табличный вид, цвета проверены на различимость при дальтонизме в обеих темах |

## Модель данных

| Таблица | Назначение |
|---|---|
| `users` | Сотрудники: роль, подразделение, доступность (замещение) |
| `categories` | Категории + правило маршрутизации (основной, резервный) |
| `tickets` | Обращения: тип, категория, статус, приоритет, автор, анонимность, ответственный, результат, SLA-сроки, дубликат |
| `events` | Неизменяемый журнал: создание, назначение, смена статуса, комментарии, внутренние заметки, вложения, поддержка |
| `supports` | «У меня тоже» по проблемам (уникально на пару обращение-сотрудник) |
| `attachments` | Метаданные файлов; файлы на диске под случайными именами |
| `notifications` | Внутренние уведомления |
| `outbox` | Журнал отправки в Битрикс24: вызовы `im.notify` и `tasks.task.add`, статус доставки, число попыток, ошибка, ID на портале |
| `b24_tasks` | Задачи Битрикс24, созданные из обращений: номер задачи, последний статус с портала, время проверки, ошибка |
| `counterparties` | Справочник клиентов из 1С УТ (`Ref_Key`, код, наименование, ИНН); у обращения — `counterparty_id` |
| `escalations` | Эскалации: одна запись на обращение и вид просрочки, время последнего напоминания и их число |
| `watchers` | Наблюдатели обращения: приглашённые коллеги и подписавшиеся |
| `settings` | Настройки, изменяемые администратором (сроки SLA, праздничные дни) |
| `impl_reports` | Отчёт о внедрении: что сделано и какой эффект |
| `reply_templates` | Шаблоны ответов, редактируемые администратором |
| `audit_log` | Журнал действий администратора |
| `surveys`, `survey_questions`, `survey_answers` | Опросы сотрудников и ответы |
| `client_feedback` | Отзывы клиентов: оценка 0–10, текст, необязательные контакты |
| `idea_votes` | Голоса за идеи: сколько голосов (1–3) сотрудник отдал идее; наружу отдаётся только сумма |
| `feedback` | Оценка результата автором: решён / не решён, комментарий |
| `sessions` | Сессии (случайный 256-битный токен, срок жизни 12 часов проверяется на сервере) |

История строится из `events` — это аудит-лог и основа аналитики «время в статусе».

## Жизненный цикл

```
new ─▶ in_review ─▶ in_progress ─▶ implemented ─▶ closed
 │        │  ▲          │
 │        ▼  │          ▼
 └─▶ need_info ◀────────┘          (ответ автора → in_review автоматически)
 └─▶ rejected ─▶ closed / повторное рассмотрение
```

Допустимые переходы — `TRANSITIONS` в `src/config.js`. Итоговые статусы требуют результата. Первый ответ фиксируется при первой смене статуса или первом публичном комментарии обработчика.

**SLA** считается в рабочих часах: суббота, воскресенье и праздничные дни из списка `HOLIDAYS` в `src/config.js` (в часовом поясе компании: по умолчанию UTC+5, Казахстан; меняется в «Настройках» или `BUSINESS_TZ_OFFSET`) пропускаются, 24 часа = 1 рабочий день; при включённых рабочих часах рабочий день — их окно. Сроки по приоритетам администратор меняет в интерфейсе (таблица `settings`); новые значения действуют для обращений, созданных после изменения.

**Эскалация:** фоновая задача раз в минуту ищет обращения с нарушенным сроком, уведомляет ответственного и руководителей и пишет запись в историю. Срок первого ответа и срок решения эскалируются независимо. Пока просрочка не устранена, напоминание повторяется каждые 2 рабочих дня (`ESCALATION_REMINDER_HOURS`); таблица `escalations` хранит время последнего напоминания.

## Безопасность

- Вход через Битрикс24 (OAuth, проверка `state`, одноразовый код, токен только от портала компании); без него рабочая установка закрыта, выбор из списка — только явно (`ALLOW_LIST_LOGIN=1`) и только во внутренней сети. С настоящим порталом выбор из списка, учебный почтовый ящик и сброс данных не включаются даже при `DEMO_MODE=1`.
- Анонимность: анонимное обращение не назначается самому автору (иначе его выдало бы имя ответственного); в разрезы по подразделениям не попадает; имена файлов автора заменяются на «Вложение N». В подсказке похожих чужие закрытые обращения сравниваются только по теме, тема чужого анонимного скрыта; поддержать «у меня тоже» можно только открытую проблему — прочие чужие обращения отвечают как несуществующие.
- Уволенные на портале: ежедневная проверка оргструктуры сразу закрывает их сессии (отключение и передачу обращений по-прежнему подтверждает администратор). Связь по ФИО для ответственных и руководителей предпросмотр выносит отдельным списком с ID портала — администратор сверяет их до применения.
- Персональные данные уволенных (`src/retention.js`): дата отключения хранится (`users.deactivated_at`); через срок, заданный администратором, — или сразу, по просьбе человека, — имя заменяется на «Бывший сотрудник №…» и в журналах действий и отправки, уведомлениях и истории обращений; рабочие контакты, связь с Битрикс24, сессии и подписки на push удаляются. Обращения и сводная статистика остаются. Обезличенную запись нельзя включить или переименовать. В журнал действий пишется только новое обозначение. Свободный текст обращений и комментариев не меняется — имя, упомянутое в нём самим пользователем, остаётся.
- Сессия в cookie `HttpOnly; SameSite=Strict`, по HTTPS — ещё и `Secure` (`COOKIE_SECURE=1` или `PUBLIC_URL` на https); мутации принимают только `application/json` (защита от CSRF через формы).
- Параметризованные SQL-запросы; валидация всех входных полей и длины на сервере.
- XSS: интерфейс вставляет пользовательский текст только через `textContent`; CSP `default-src 'self'`, без inline-скриптов; `nosniff`. Показ во фрейме запрещён (`X-Frame-Options: DENY`), кроме страниц интерфейса, когда настроен вход через Битрикс24: их разрешено показывать только порталу компании (`frame-ancestors <портал>`), в демо — самому серверу.
- Внутри портала: форму с ключом сотрудника система принимает только со страницы портала (заголовок `Origin`), ключ проверяет сам портал, а `app.info` подтверждает, что ключ выдан именно нашему приложению — ключ стороннего приложения портала не подходит. Cookie сессии во фрейме по HTTPS — `SameSite=None; Secure; Partitioned`: браузер хранит её отдельно, только для фрейма на портале; изменяющие запросы по-прежнему принимают только JSON. Cookie `state` по HTTPS — с префиксом `__Host-`, её нельзя подложить с соседнего поддомена.
- Вложения: белый список расширений, лимит 5 МБ, случайные имена файлов, отдача как `application/octet-stream` с `Content-Disposition: attachment` и `Cache-Control: no-store`, доступ только при праве на обращение. Сервис-воркер не кэширует API и демо-портал.
- Защита от выхода за пределы каталога статики; ограничение размера тела запроса; rate limit на изменяющие запросы (60 в минуту на пользователя, для входа — на адрес; меняется переменной `MUTATIONS_PER_MINUTE`, в сквозных тестах поднят). За своим HTTPS-прокси (`TRUST_PROXY=1`) адрес берётся из последнего значения `X-Forwarded-For` (его дописал прокси, левые подставляет клиент) — иначе все пользователи делили бы один лимит адреса прокси. У формы клиентов и выгрузки для 1С — отдельные счётчики по адресу. Битая кодировка в адресе — ответ 400, а не ошибка сервера.
- Ошибки не раскрывают внутренние детали; чужие обращения отдаются как 404.
- Экспорт CSV: значения, начинающиеся с `=`, `+`, `-`, `@`, экранируются — защита от выполнения формул в Excel.
- Анонимные обращения: имя и подразделение не отдаются API никому, кроме автора; фильтр по подразделению их исключает; в рейтинге авторов они не участвуют.
- Идеи коллег: обращение становится видимым всем только по решению автора; автор и ответственный могут снять публикацию. Читатели и подписчики не видят внутренние заметки и не могут прикладывать файлы. Рейтинг авторов строится только по опубликованным неанонимным обращениям.
- Опросы: сводные результаты доступны только после закрытия опроса и при трёх и более ответивших (иначе по разнице итогов «до» и «после» можно вычислить отвечавшего); закрытый опрос не открывается заново; тексты показываются при трёх и более непустых ответах и отсортированы по алфавиту.
- Публичная форма для клиентов (`POST /api/public/feedback`) — единственный изменяющий метод без входа в рабочем режиме (в демо-режиме без входа открыт ещё встроенный демо-портал `/demo-portal/…`, его журнал вызовов ограничен 100 записями): строгая проверка полей, поле-ловушка от ботов, отдельный лимит 5 запросов в минуту с адреса и общий предел 300 отзывов в сутки; оценка принимается только числом. Для открытого интернета нужны капча и модерация.
- Отключённый пользователь не может войти, его сессии удаляются, ему нельзя назначить обращение, а его открытые обращения автоматически переходят следующему по правилу категории; изменения настроек записываются в журнал действий.
- Сброс демо-данных (`POST /api/admin/demo-reset`) доступен только администратору и только в демо-режиме, который включается явно (`DEMO_MODE=1`; так делают `npm start` и `npm run reset`, в Docker-образе он выключен), иначе метод отвечает 403. Очистка и повторное заполнение идут одной транзакцией; удаляются все сессии и только файлы вложений.
- Журнал отправки в Битрикс24: у анонимного обращения скрыты имена всех получателей уведомлений, чтобы автора нельзя было вычислить по разнице.
- Импорт пользователей принимает до 500 строк и 60 тысяч символов; строки с ошибками не добавляются и возвращаются с причиной.
- Приглашение в обсуждение одинаково обрабатывает автора анонимного обращения и любого другого коллегу, чтобы по ответу нельзя было вычислить автора.
- Рабочий запуск без демо-данных: `DEMO_DATA=0` — в пустой базе только администратор (`ADMIN_B24_ID` связывает его с порталом). Без входа через Битрикс24 (`B24_CLIENT_ID`) вход — выбор пользователя без пароля, поэтому такую установку размещают только во внутренней сети или за VPN.
- Сессия продлевается, пока человек работает (после половины 12-часового срока отсчёт начинается заново; фоновый опрос уведомлений не считается), но не дольше недели с входа; без работы — истекает. Резервные копии базы и вложений: `npm run backup` или раз в сутки при `BACKUP_DIR` (`VACUUM INTO` — без остановки сервера), хранятся последние 14; каталог доступен только владельцу процесса, сессий в копии нет.
- **Промышленная версия:** HTTPS, журнал доступа, шифрование диска с вложениями, антивирусная проверка файлов.

## Интеграции

ТЗ (раздел 1.2) называет три цели, ради которых интеграция полезна: назначение ответственных, уведомления и последующий анализ обращений. В компании используются Битрикс24 и 1С УТ; ниже — что берём из каждой системы и зачем.

| Система | Цель (ТЗ 1.2) | Данные и направление | Способ | Уточнить перед реализацией |
|---|---|---|---|---|
| Битрикс24 — оргструктура | Назначение ответственных: актуальные сотрудники, подразделения и их руководители | Б24 → система: ID, ФИО, подразделение, руководитель подразделения, признак «уволен» | REST `department.get`, `user.get` через входящий вебхук: по кнопке; раз в сутки — проверка и уведомление администратору, применение после его подтверждения | Где ведётся оргструктура (в Б24 или только в 1С ЗУП), права вебхука на чтение пользователей |
| Битрикс24 — уведомления | Уведомления там, где сотрудники уже работают | Система → Б24: получатель (ID в Б24), текст, ссылка на обращение | REST `im.notify` | Разрешено ли приложению писать в чаты, системные или личные уведомления |
| Битрикс24 — задачи | Исполнение реализуемых предложений в привычном инструменте | Система → Б24: задача из обращения (название, ответственный, срок); Б24 → система: номер задачи | REST `tasks.task.add` | Проекты/группы для задач, сопоставление статусов задачи и обращения |
| Битрикс24 — вход | Вход корпоративной учётной записью вместо демо-входа | Б24 → система: ID и ФИО пользователя | OAuth 2.0 локального приложения облачного портала (`B24_CLIENT_ID`, `B24_CLIENT_SECRET`), метод `user.current` | Регистрация приложения на портале (путь обработчика `<PUBLIC_URL>/api/auth/b24/callback`, права `user`), адрес системы по HTTPS |
| Битрикс24 — система внутри портала | Сотрудник открывает систему пунктом левого меню портала, не уходя из Битрикс24, и входит без отдельного пароля | Б24 → система: пользователь портала при открытии (подписанный запрос приложения) | Локальное приложение облачного портала: обработчик `POST <PUBLIC_URL>/api/auth/b24/app` для левого меню (`LEFT_MENU`) и вкладки задачи (`TASK_VIEW_TAB` — исходное обращение); ключ `AUTH_ID` проверяется методом `user.current` на портале компании — сделано | Адрес системы по HTTPS; привязка вкладки задачи (`placement.bind`) при установке приложения; проверить на портале, что форма приходит с адреса портала (заголовок `Origin`) |
| 1С УТ — клиенты | Анализ: связать обращение с клиентом, по которому возникла проблема | 1С → система: справочник контрагентов (код, наименование, ИНН) | OData-интерфейс 1С (`Catalog_Контрагенты`), по кнопке и автоматически раз в сутки | Публикация OData на сервере 1С, учётная запись только на чтение, какие контрагенты нужны (клиенты, поставщики) |
| 1С УТ — выгрузка для анализа | Последующий анализ обращений рядом с продажами и закупками | Система → 1С: обращения без персональных данных автора анонимных (категория, подразделение, статус, даты, клиент) | HTTP-метод системы с токеном, 1С забирает данные регламентным заданием | Куда в 1С складывать данные, частота выгрузки |

**У компании облачный Битрикс24** — что из этого следует:

- Подключение не требует доработки кода: администратор портала создаёт входящий вебхук («Разработчикам» → «Другое» → «Входящий вебхук») с правами на пользователей, структуру компании, уведомления и задачи, адрес вебхука задаётся в `B24_WEBHOOK_URL`.
- Серверу системы нужен исходящий доступ в интернет к адресу портала (`*.bitrix24.kz` / `*.bitrix24.ru`) по HTTPS.
- Ссылки в уведомлениях открываются из Битрикс24, поэтому `PUBLIC_URL` — адрес системы, доступный сотрудникам: внутренний (офис, VPN) или внешний.
- Вход через Битрикс24 — через локальное приложение портала (OAuth 2.0): администратор портала регистрирует приложение и передаёт его код и ключ. Портал возвращает сотрудника в систему переходом в его же браузере, а код на токен сервер меняет у `oauth.bitrix.info` — нужен исходящий доступ к нему. Адрес системы — по HTTPS (защищённая cookie).
- Обратная связь по статусу задачи: облачный портал отправляет события (`ONTASKUPDATE`) только на адрес, доступный из интернета. Поэтому в MVP статусы опрашиваются по расписанию (`tasks.task.get`, раз в 5 минут) — это работает и во внутренней сети.
- Уточнить у компании: тариф (на части тарифов облака REST и вебхуки ограничены), кто из администраторов портала создаёт вебхук, где размещается система — только во внутренней сети или с внешним адресом.

Почему оргструктура из Битрикс24, а не из 1С УТ: 1С УТ — конфигурация для торговли и склада, кадровой структуры и руководителей в ней обычно нет (она в 1С ЗУП). В Битрикс24 сотрудники, отделы и руководители отделов есть всегда — они нужны самому порталу. Из 1С УТ берём то, что в ней действительно ведётся: клиентов.

**Что сделано в MVP** (`src/integrations/`):

- Битрикс24 — оргструктура, уведомления и задачи работают через входящий вебхук (`B24_WEBHOOK_URL`). Оргструктура: предпросмотр изменений, затем применение (сопоставление по ID Битрикс24, при первой загрузке — по ФИО, кроме администраторов и одинаковых ФИО; руководители отделов получают роль ответственного; уволенные отключаются, их обращения уходят резервным). Уведомления и задачи пишутся в `outbox` в той же транзакции, что и изменение обращения, и отправляются в фоне: до 5 попыток с растущей паузой, затем статус «Ошибка» и ручной повтор. Номер созданной задачи записывается в историю обращения. Ответ портала проверяется: `im.notify` с `result: false` — не доставка; задача без сопоставленного ответственного (`RESPONSIBLE_ID` обязателен) ждёт загрузки оргструктуры. Сброс демо-данных отменяет запись результатов отправок, начатых до него.
- 1С УТ — справочник контрагентов по OData (`Catalog_Контрагенты`, помеченные на удаление не предлагаются) и выгрузка обращений `GET /api/integrations/1c/tickets?since=…` по токену `ONEC_EXPORT_TOKEN`: без текста, без автора, у анонимных скрыто подразделение; лимит 5 запросов в минуту с адреса. `since` сравнивается с `changedAt` — временем последнего изменения с учётом новых «У меня тоже»; объединённые дубликаты выгружаются с `duplicateOf`, чтобы 1С исключила их из анализа.
- Демо-портал (`src/integrations/demo-portal.js`) — в демо-режиме без переменных окружения система ходит по HTTP на `/demo-portal/…` того же сервера; он отвечает в форматах REST Битрикс24 и OData 1С и содержит синтетические отличия от демо-датасета (новые, переведённые, уволенные сотрудники; контрагент, помеченный на удаление).
- Статусы задач (`src/integrations/b24-tasks.js`): раз в 5 минут и по кнопке «Проверить статусы задач» система запрашивает `tasks.task.get` по открытым обращениям. Изменение статуса попадает в историю обращения; когда задача «Ждёт контроля» или «Завершена», ответственный получает уведомление зафиксировать итог — сам статус обращения не меняется автоматически, итог фиксирует человек. Задача, удалённая на портале, помечается ошибкой, остальные проверяются дальше.
- Ежедневная синхронизация (`src/integrations/daily.js`): через минуту после запуска и раз в сутки контрагенты из 1С загружаются автоматически (с записью в журнал действий), а оргструктура Битрикс24 только проверяется — если на портале есть изменения, администраторы получают одно уведомление со сводкой («новых: 3, уволено: 1…»), применяет их администратор. Об одних и тех же изменениях повторно не сообщается.
- Аналитика по клиентам: на странице «Показатели» — клиенты 1С с наибольшим числом обращений; ссылка ведёт в реестр с отбором `counterparty`.
- Вход через Битрикс24 (`src/integrations/b24-sso.js`): кнопка на экране входа → страница входа портала → возврат с одноразовым кодом; сервер меняет код на токен у `oauth.bitrix.info`, проверяет, что токен выдан порталом компании (`client_endpoint`), и узнаёт сотрудника методом `user.current`. Сотрудник находится по ID Битрикс24 — связь появляется при загрузке оргструктуры; не связанный или отключённый получает понятное сообщение. Защита: случайный `state` в cookie (`HttpOnly; SameSite=Lax`, 10 минут — вход завершает тот браузер, который его начал), код одноразовый, ключ приложения не уходит в браузер, токен портала не хранится — после входа обычная сессия. Уволенный на портале (`ACTIVE` = нет) не входит сразу, не дожидаясь ежедневной проверки. Связь с порталом открывает вход, а ФИО в профиле портала сотрудник может поменять сам, поэтому по ФИО не связываются администраторы и одинаковые ФИО на портале — в предпросмотре они показаны как «Не связаны автоматически». Когда подключён настоящий портал, вход выбором из списка и список сотрудников (`/api/demo-users`) закрыты, кнопка в шапке — «Выйти»; первого администратора связывает с порталом `ADMIN_B24_ID`. В демо-режиме страницу входа портала имитирует демо-портал.
- Система внутри портала: Битрикс24 открывает адрес приложения во фрейме и присылает формой ключ текущего сотрудника (`AUTH_ID`) и место встраивания. Система проверяет, что форма пришла со страницы портала, узнаёт сотрудника методом `user.current` и открывает главную (пункт меню) или обращение, из которого создана задача (вкладка `TASK_VIEW_TAB`, `PLACEMENT_OPTIONS.taskId`). На демо-портале это показано страницей `/demo-portal/b24/`: меню портала, задачи и фрейм с системой.
- Ручное связывание (`POST /api/admin/integrations/b24/link`): кого система не связала по ФИО, администратор связывает сам; сотрудник проверяется на портале (`user.get`) — связать можно только действующего и ещё не связанного. Действие пишется в журнал. Отвязка (`POST /api/admin/integrations/b24/unlink`, кнопка в таблице пользователей) снимает связь и сразу закрывает сессии этого человека; свою связь администратор снять не может.
- Письма-уведомления (`src/integrations/smtp.js`): каждое уведомление пишется в журнал отправки и по каналу «почта» — для сотрудников с рабочей почтой, не отключивших письма. Отправка — тем же фоновым механизмом, что и Битрикс24 (повторы, «Ошибка», ручной повтор). SMTP-клиент без зависимостей: STARTTLS или TLS, проверка сертификата, пароль только по шифрованному соединению, письмо без шифрования не уходит (кроме своего компьютера и `SMTP_ALLOW_PLAIN=1`), заголовки в UTF-8 без переводов строк, тело в base64; адреса из ответов сервера в журнал не попадают. В демо-режиме — учебный SMTP-сервер только на 127.0.0.1 (`demo-smtp.js`), у писем об анонимных обращениях адрес на странице демо-почты скрыт.
- Push-уведомления (`src/integrations/webpush.js`): Web Push без зависимостей. Ключи сервера P-256 (VAPID) создаются при первом запуске или задаются `VAPID_*`; запрос к службе push подписан ES256-JWT на 12 часов, текст зашифрован по RFC 8291 (aes128gcm; реализация проверена эталоном из RFC). Подписка устройства (`push_subscriptions`) принимается только для служб push браузеров (HTTPS, без порта и логина), перенаправления не выполняются — сервер нельзя заставить слать запросы во внутреннюю сеть. Отправка — через тот же журнал (канал `push`), на все устройства сотрудника сразу; отозванные подписки (404/410) удаляются. Не больше 10 устройств на сотрудника; при выходе из системы устройство отписывается.
- Производственный календарь (`src/integrations/calendar.js`): `GET {PROD_CALENDAR_URL}api/getdata?year&cc` — строка из 365/366 цифр; нерабочие будни становятся праздниками, рабочие субботы и воскресенья — рабочими выходными (`settings.workdays`), расчёт сроков учитывает оба списка. Загрузка заменяет даты только выбранного года. Наружу уходят год и код страны.
- Безопасность: адрес вебхука и пароль 1С — только в переменных окружения, интерфейс показывает лишь хост. Журнал анонимного обращения по-прежнему скрывает получателей. Записи журнала из прежней версии при миграции помечаются как имитация и не отправляются задним числом.

Принцип: система остаётся источником правды по обращениям; интеграции добавляются как адаптеры, не меняя ядро.

## Масштабирование и развитие

- **Нагрузка:** ожидаемый объём (сотни обращений в месяц) SQLite выдерживает с запасом. `npm run loadtest` на 10 000 обращений и 1 000 сотрудников: реестр, поиск, канбан, карточка, подача — до 70 мс; главная руководителя, показатели и сводка недели — около 0,2 с; выгрузка в Excel и эскалация — около 0,1 с. На 30 000 обращений тяжёлые экраны — 0,3–0,8 с: аналитика считается в памяти по всем обращениям, следующий шаг — агрегаты в SQL и кэш на минуту. Поиск похожих пар в аналитике ограничен 400 последними открытыми обращениями. Для нескольких инстансов — PostgreSQL, сессии в БД уже есть, вложения — в S3-совместимое хранилище.
- **Поиск дубликатов:** заменить префиксный стемминг на полнотекстовый поиск PostgreSQL (русская морфология) или эмбеддинги.
- **SLA:** рабочие часы — одно окно для всей компании; часовой пояс задаётся компании и, для филиалов, подразделению (срок — по поясу подразделения ответственного).
- **Новые типы обратной связи** (клиенты, опросы): отдельные сущности и права поверх того же журнала событий; внешний контур — отдельный публичный интерфейс без доступа к внутренним обращениям.

Покрытие строк серверного кода — около 98%.

На GitHub запуск сейчас выключен из-за ограничения GitHub Actions в аккаунте — проверки выполняются локально теми же командами; включается снова командой `gh workflow enable CI`.
