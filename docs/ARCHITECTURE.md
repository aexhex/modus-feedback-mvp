# Техническая концепция

## Компоненты

```
Браузер (SPA, ES-модули)  ──HTTP/JSON──▶  Node.js сервер (node:http)
                                           ├─ routes.js     REST API, конверт { ok, data, error }
                                           ├─ access.js     политика доступа (RBAC + владение)
                                           ├─ routing.js    маршрутизация обращений
                                           ├─ tickets-*.js  жизненный цикл, SLA, комментарии
                                           ├─ analytics.js  показатели, повторяющиеся темы
                                           ├─ notifications.js  внутренние уведомления (точка интеграции)
                                           └─ db.js ──▶ SQLite (node:sqlite) + data/uploads/
```

## Выбор технологий

| Решение | Почему |
|---|---|
| Node.js 24+, без внешних зависимостей | Запуск одной командой без `npm install`; нет цепочки поставок для проверки; встроенные `node:sqlite` и `node:test` |
| SQLite | Реляционная модель, транзакции, ноль администрирования для MVP. Схема переносится на PostgreSQL без изменений логики |
| Vanilla JS + ES-модули | Нет шага сборки; интерфейс простой. При росте — React/Vue |
| Хэш-роутинг SPA | Работает на любом статическом хостинге / за любым прокси |

## Модель данных

| Таблица | Назначение |
|---|---|
| `users` | Сотрудники: роль, подразделение, доступность (замещение) |
| `categories` | Категории + правило маршрутизации (основной, резервный) |
| `tickets` | Обращения: тип, категория, статус, приоритет, автор, анонимность, ответственный, результат, SLA-сроки, дубликат |
| `events` | Неизменяемый журнал: создание, назначение, смена статуса, комментарии, внутренние заметки, вложения, поддержка |
| `supports` | «Поддержать» (уникально на пару обращение-сотрудник) |
| `attachments` | Метаданные файлов; файлы на диске под случайными именами |
| `notifications` | Внутренние уведомления |
| `sessions` | Сессии (случайный 256-битный токен) |

История строится из `events` — это аудит-лог и основа будущей аналитики «время в статусе».

## Жизненный цикл

```
new ─▶ in_review ─▶ in_progress ─▶ implemented ─▶ closed
 │        │  ▲          │
 │        ▼  │          ▼
 └─▶ need_info ◀────────┘          (ответ автора → in_review автоматически)
 └─▶ rejected ─▶ closed / повторное рассмотрение
```

Допустимые переходы — `TRANSITIONS` в `src/config.js`. Итоговые статусы требуют результата. Первый ответ фиксируется при первой смене статуса или первом публичном комментарии обработчика.

## Управление доступом

| Действие | Сотрудник | Ответственный | Руководитель | Админ |
|---|---|---|---|---|
| Создать, комментировать своё | ✓ | ✓ | ✓ | ✓ |
| Видеть обращение | свои | свои + назначенные | все | все |
| Менять статус/приоритет, внутренние заметки | — | назначенные | все | все |
| Переназначить | — | — | ✓ | ✓ |
| Аналитика | — | — | ✓ | ✓ |
| Категории, маршрутизация, замещение | — | — | — | ✓ |

Проверки выполняются на сервере (`src/access.js`); интерфейс лишь скрывает недоступные действия.

## Безопасность

- Сессия в cookie `HttpOnly; SameSite=Strict`; мутации принимают только `application/json` (защита от CSRF через формы).
- Параметризованные SQL-запросы; валидация всех входных полей и длины на сервере.
- XSS: интерфейс вставляет пользовательский текст только через `textContent`; CSP `default-src 'self'`, без inline-скриптов; `X-Frame-Options: DENY`, `nosniff`.
- Вложения: белый список расширений, лимит 5 МБ, случайные имена файлов, отдача как `application/octet-stream` с `Content-Disposition: attachment`, доступ только при праве на обращение.
- Защита от выхода за пределы каталога статики; ограничение размера тела запроса; rate limit на изменяющие запросы (60/мин на пользователя).
- Ошибки не раскрывают внутренние детали; чужие обращения отдаются как 404.
- **Промышленная версия:** HTTPS, SSO вместо демо-входа, срок жизни сессий, резервное копирование БД, журнал доступа, шифрование диска с вложениями, антивирусная проверка файлов.

## Интеграции (предложение, в MVP не реализованы)

| Система | Цель | Данные и направление | Способ | Уточнить |
|---|---|---|---|---|
| Битрикс24 — авторизация | Вход корпоративной учётной записью | Б24 → система: ID, ФИО, подразделение | OAuth 2.0 приложения Б24 | Тип портала (облако/коробка), права приложения |
| Битрикс24 — уведомления | Уведомлять там, где работают сотрудники | Система → Б24: текст, ссылка, получатель | REST `im.notify` (точка — `src/notifications.js`) | Разрешено ли приложению писать в чаты |
| Битрикс24 — задачи | Исполнение реализуемых предложений в привычном инструменте | Система → Б24: задача из обращения; Б24 → система: статус задачи | REST `tasks.task.add` + вебхук событий | Проекты/группы для задач, сопоставление статусов |
| 1С | Актуальный справочник сотрудников, подразделений, руководителей | 1С → система, раз в сутки | Выгрузка через HTTP-сервис / OData 1С | Конфигурация (ЗУП/УТ), где ведётся оргструктура |

Принцип: система остаётся источником правды по обращениям; интеграции добавляются как адаптеры, не меняя ядро.

## Масштабирование и развитие

- **Нагрузка:** ожидаемый объём (сотни обращений в месяц) SQLite выдерживает с запасом. Для нескольких инстансов — PostgreSQL, сессии в БД уже есть, вложения — в S3-совместимое хранилище.
- **Поиск дубликатов:** заменить префиксный стемминг на полнотекстовый поиск PostgreSQL (русская морфология) или эмбеддинги.
- **SLA:** рабочий календарь, эскалация руководителю по расписанию (фоновая задача).
- **Новые типы обратной связи** (клиенты, опросы): отдельные сущности и права поверх того же журнала событий; внешний контур — отдельный публичный интерфейс без доступа к внутренним обращениям.

## Тестирование

`npm test` — 40 тестов (`node:test`): доступ по ролям, маршрутизация и резервирование, переходы статусов, уточнения, внутренние заметки, анонимность, дубликаты, SLA и фильтры, аналитика, вложения, безопасность статики и JSON. Покрытие строк серверного кода — около 97%.
